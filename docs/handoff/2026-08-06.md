## Completed Tickets

### ✅ #39 — 06 Crawler (login + discovery + download)

**What was built:**
- `backend/crawler/session.py` — `CrawlSession` with dual auth modes (login + public), form extraction via `input[type=password]`, re-auth on expiry, old-client cleanup on re-login
- `backend/crawler/discover.py` — paginated HTML parsing with CSS selectors, auto-walk with visited-URL tracking + MAX_PAGES cap, manual pagination with stored state, spatial-file filtering (URL path extension match, not substring), filename extraction from URLs when link text is generic
- `backend/crawler/download.py` — batched download queue (ThreadPoolExecutor), per-file progress via WebSocket, filename sanitization (path traversal prevention), ETag + Last-Modified capture, indeterminate progress (null) for unknown-size files
- `backend/crawler/respect.py` — robots.txt enforced (raises `RobotsDisallowed`), consistent Chrome UA for both robots.txt and requests, randomized 1–3s delays between pages
- `backend/crawler/state.py` — `crawl_state` in plain DuckDB catalog (not DuckLake — DuckLake doesn't support PRIMARY KEY or INSERT OR REPLACE), DELETE+INSERT with UNIQUE INDEX, ETag/Last-Modified comparison for change detection, `dataset_name` linkage for cleanup/re-download, preserve-existing on re-write
- `backend/crawler/__init__.py` — package marker

**API endpoints added:**
```

GET    /api/crawler/session-status     — check authenticated/expired
POST   /api/crawler/logout             — clear session

POST   /api/crawler/cleanup/{dataset}  — delete source files, mark crawl_state as cleaned
POST   /api/crawler/redownload/{dataset} — re-download from original URLs
GET    /api/tables/{name}/sources      — crawl_state entries linked to a DuckLake table
```

**Frontend changes:**
- `CrawlerPanel.tsx` — Public/Login toggle, URL-only public mode, env-var auto-fill with mode suggestion, 30-second session polling, file grid with filter/select-all/status, download queue with per-file progress bars (indeterminate for unknown-size with animated pulse), "Open in Pipeline" button feeds downloaded dir to FileGrid
- `DuckLakeConsole.tsx` — Per-table source files section (expands with snapshots), colored status dots, Clean Up button (amber, when files on disk), Re-download button (blue, when files cleaned), filesizes and ETag display
- `App.tsx` — `handleCrawlerFiles` uses `handleScan(dir)` for proper FileEntry, `handleCrawlerScanDir` passes through to DirectoryPicker, "Crawler" nav tab added
- `DirectoryPicker.tsx` — Updated remote URL placeholder to point to Crawler tab

**Key decisions (see ADR #5):**
- Files downloaded to disk as intermediate storage (not DuckDB tables) — avoids single-writer contention with parallel downloads, preserves raw format for debugging
- Discovery runs in `ThreadPoolExecutor` so the event loop stays responsive and Stop works
- `crawl_state` stored in plain DuckDB catalog, not DuckLake — principled separation of app metadata vs. lakehouse data
- robots.txt enforced (disallowed URLs are refused, not just warned)

## Known Issues

### 🟠 Cleanup / Re-download buttons not visible in DuckLake Console

The frontend code for the source-files section is built and deployed (verified: "Clean Up" and "Re-download" strings exist in `dist/assets/index-BjYvRsrr.js`). The section renders inside an expanded table row when `sourceFiles.length > 0` and `!sourceLoading`. Possible causes:

1. **Browser cache** — This is the same known issue from the 2026-08-05 handoff: after `npm run build`, the browser may serve a cached JS bundle with stale UI. Users must hard-refresh (**Ctrl+Shift+R**) to see new features.
2. **No expanded table** — The source-files section only renders when a table row is clicked to expand it. Make sure you've clicked the `test_countries` row in the DuckLake console to expand it.
3. **No linked source files** — The section only renders when `sourceFiles.length > 0`. Source files are automatically linked after a pipeline run on crawler-downloaded files. If you haven't run a pipeline, no sources will show. The data is available: `GET /api/tables/test_countries/sources` returns 2 entries.

To verify the backend is working:
```bash
curl -s http://127.0.0.1:8000/api/tables/test_countries/sources | python -m json.tool
```

This should return 2 source entries with `status: "done"` or `status: "cleaned"`.

### 🟡 data.nextgis.com returns 0 files

The crawler's fallback link scanner finds only `<a>` tags whose `href` ends with a spatial extension. data.nextgis.com's home page links to category pages (e.g., `/en/catalog/subdivisions/`), not directly to spatial files. The crawl needs a starting URL deeper in the catalogue.

### 🟡 Crawl state entries accumulate for repeated re-downloads

Each `upsert_entry` call does DELETE + INSERT, so the same URL appears once. But repeated redownload cycles create new `downloaded_at` timestamps. The list keeps growing only if new URLs are downloaded. Low impact.

## Quick Test

```bash
# 1. Connect (public mode)
curl -s -X POST http://127.0.0.1:8000/api/crawler/login \

  -H "Content-Type: application/json" \
  -d '{"auto":true,"page_url":"https://geojson.xyz/"}'

# 3. Download (pick a couple of small files)
curl -s -X POST http://127.0.0.1:8000/api/crawler/download \
  -H "Content-Type: application/json" \

    {"name":"ne_110m_admin_0_tiny_countries.geojson","url":"https://...cloudfront.net/..."},
    {"name":"ne_110m_wgs84_bounding_box.geojson","url":"https://...cloudfront.net/..."}
  ]}'

# 4. Run pipeline
curl -s -X POST http://127.0.0.1:8000/api/run-pipeline \
  -H "Content-Type: application/json" \
  -d '{"paths":["/path/to/downloads/ne_110m_admin_0_tiny_countries.geojson","/path/to/downloads/ne_110m_wgs84_bounding_box.geojson"],"dataset_name":"test_countries","column_mapping":[]}'

# 7. Re-download
curl -s -X POST http://127.0.0.1:8000/api/crawler/redownload/test_countries
```
