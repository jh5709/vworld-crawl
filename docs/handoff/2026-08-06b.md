# Handoff — 2026-08-06 (post-40 bug hunt)

## Session Summary

Performed a deep diagnosis of issue #40 after the initial code-review fixes. Traced 6 bug chains across the full re-crawl → delta pipeline → map preview stack. **5 bugs fixed, 1 deferred** (Bug 2b proved unnecessary after DuckLake upstream research — schema evolution handles column addition transparently).

## Bugs Found & Fixed

### Bug 1 — delta_date chain broken (FATAL)

**Root**: Backend `POST /api/crawler/recrawl` correctly computes `delta_date` per-file from filename patterns (`_detect_delta_date()`), but the frontend dropped it at three points:

- `CrawlFile` type lacked `delta_date` field → JSON silently stripped it
- `handleRecrawl()` never captured/forwarded delta dates to App state
- `onFilesDownloaded` callback only carried `{name, path}` — no delta metadata bridge

**Fix**:
- `CrawlerPanel.tsx`: Added `delta_date?: string` to `CrawlFile` interface; `_urlToDeltaDate` ref (URL→deltaDate) populated during recrawl; new `onRecrawlDelta` prop forwards `{name, path, deltaDate}` after download completes
- `App.tsx`: Added `_recrawlDeltaMap` ref (path→deltaDate); `handleRecrawlDelta` handler stores it; `handleInspect` auto-fills `dataDate` + `deltaMode` when file matches a known delta

### Bug 2a — Single data_date for all files (HIGH)

**Cause**: `run_pipeline()` accepted one `data_date` string; all files in a pipeline got the same date, defeating per-file delta detection.

**Fix**:
- `PipelineRequest` model: added `data_dates: list[str]` parallel to `paths`
- `runner.py`: `data_dates` parameter — per-file index lookup; falls back to global `data_date`
- `main.py` WS handler: extracts `data_dates` from WS params
- `App.tsx`: builds `data_dates` vector from `_recrawlDeltaMap` when `deltaMode` is active

### Bug 5 — regex lacks word boundaries (LOW)

**Cause**: `_detect_delta_date()` patterns matched any 8-digit substring (e.g., `"2015"` inside IDs).

**Fix**: Added `\b` anchors: `r'\b(\d{4})(\d{2})(\d{2})\b'` and `r'\b(\d{4})-(\d{2})-(\d{2})\b'`.

### Bug 4 — POST /features (LOW)

**Fix**: Changed `POST /api/tables/{name}/features` with `FeaturesRequest` body → `GET` with optional query params (`?xmin=&ymin=&xmax=&ymax=&limit=`). Updated `MapPreview.tsx` to use `URLSearchParams`.

### Bug 3 — COUNT refinement (LOW)

**Assessment**: Parquet metadata + zone-map pruning makes `COUNT(*)` near-instant for DuckLake tables. The concern about unbounded full-table scans was overstated. Kept the existing query with an explanatory comment.

## Bug 2b — Schema evolution (DEFERRED — proven safe by upstream)

**Concern**: Upserting a delta file (with `data_date` column) into a table created without `data_date` = schema mismatch.

**Upstream research**:
- **DuckLake** supports `ALTER TABLE ADD COLUMN` without rewriting data files via field-ID resolution. New Parquet files containing extra columns auto-trigger schema evolution. Ignor files return NULL for the new column.
- **duckle v0.4.0** added "Merge" write mode using `MERGE INTO` for DuckLake (since DuckLake doesn't support primary keys/`ON CONFLICT`).
- See: ducklake. select/docs/stable/duckdb/usage/schema_evolution and ducklake. select/docs/stable/duckdb/usage/upserting

**Verdict**: No code change needed. DuckLake handles the scenario gracefully. A manual end-to-end integration test is the only follow-up.
