## Decision Change from ADR

**Shapefile reading uses DuckDB Spatial, not fiona/GDAL.** The original plan was fiona, but DuckDB's `ST_Read()` handles everything we need (CRS via `ST_CRS`, geometry type via `ST_GeometryType`, validity via `ST_IsValid`) with zero extra dependencies. This aligns with ADR #2's zero-dependency principle. `.zip` files are unzipped to a temp directory first (stdlib `zipfile`), then read as `.shp`.

### ✅ #36 — 03 Pipeline execution

**What was built:**
- `backend/pipeline/runner.py` — Duckle pipeline runner wrapping the full flow
- `POST /api/run-pipeline` endpoint + frontend "Run Pipeline" button
- `GET /api/tables` + `GET /api/tables/{name}` — quick DuckLake data viewer

**Gotchas discovered:**
- `qa.geomvalidate` mode values are `"valid"` / `"invalid"` (not `"keep_valid"` / `"keep_invalid"`)
- `p.rename(col="new_name")` works; `p.transform("xf.rename", col="new_name")` does NOT
- Shapefiles can't mix geometry types — GDAL converts all to the first type found
- DuckLake doesn't support indexes; post-crawl merge + spatial index are non-fatal
- **`.zip` files:** duckle's `src.spatial` can't read `.zip` directly. The runner imports `_unzip_shapefile` from `schema_detector.py` to extract `.zip` → `.shp` before passing to duckle

**Data in catalog:** `roads` (4 rows), `buildings` (2 rows), `실험2` (2,507 rows of real VWorld data) at `catalog/ducklake_metadata.ducklake`

### ✅ #37 — 04 Real-time pipeline progress

**What was built:**
- `backend/pipeline/progress.py` — parses duckle stdout into per-node stats
- `GET /api/pick-directory` — native folder picker via zenity/kdialog with fallback
- `/ws/pipeline` WebSocket endpoint — streams progress events during pipeline execution
- `PipelineProgress` component — animated per-node cards with status icons + row counts
- Source mode toggle: **Local Directory** (path + Browse + drag-drop) / **Remote URL** (placeholder for crawler)
- Pipeline runs in background thread (`asyncio.wrap_future`) so WebSocket stays responsive

**Gotchas discovered:**
- **DuckLake table listing:** use `SELECT name FROM sqlite_master WHERE type='table'` — `information_schema.tables WHERE table_schema='vworld'` returns empty because ATTACHed DuckLake tables are in `main` schema, not a schema named after the database
- **WebSocket progress:** pipeline must run in a thread (`ThreadPoolExecutor`) — `future.result()` blocks the event loop, use `asyncio.wrap_future(future)` instead
- DuckDB reuses the `sqlite_master` name for its system catalog (no actual SQLite involved)

### ✅ #38 — 05 DuckLake console

**What was built:**
- `backend/db.py` — shared connection helper (DuckLake ATTACH, `SET TimeZone='Asia/Seoul'`, identifier quoting, paths anchored to backend dir instead of CWD)
- `backend/ducklake_console.py` — table list with latest snapshot version + last-modified, per-table snapshot timeline (via `ducklake_snapshot_changes`, not whole-catalog range), row preview, compact, rewrite-data-files, catalog-wide snapshot expiry with dry-run + space reclaim
- `POST /api/ducklake/expire-snapshots?days=&dry_run=` — catalog-level expiry (DuckLake expires per catalog, not per table)
- Console tab in the nav; toolbar with Refresh + Expire dialog (dry-run preview required before Expire button enables)

**Gotchas discovered:**
- **Console tab never rendered** — the nav mapped over `["picker","grid","schema"]` and `"console"` was missing; not a browser-cache issue
- `ducklake_expire_snapshots(catalog, older_than => TIMESTAMPTZ, dry_run => BOOL)` — first arg is the **catalog**, not the table; naive TIMESTAMP fails to bind
- `ducklake_cleanup_old_files('vworld')` actually reclaims disk; expiry alone only marks files in `ducklake_files_scheduled_for_deletion`
- **DuckLake does not support indexes at all** — the RTREE button now returns a friendly "unsupported" note pointing at the bbox columns
- `ducklake_merge_adjacent_files(catalog, table)` — arg order matters; `post_crawl_compact` had them swapped (silently swallowed by try/except)
- System TZ was `Asia/Pyongyang` — all connections now pin `SET TimeZone='Asia/Seoul'`
- duckle's `snk.ducklake` ignores `dataPath`; Parquet files land in the default `<metadata>.ducklake.files/` dir
- Vite proxies `/api` and `/ws` to :8000, so the frontend uses same-origin relative URLs (no more hardcoded `localhost:8000`)

**Follow-up (same day) — multi-format support + spatial index removal:**
- Source formats now: `.zip` (any spatial file inside), `.shp`, `.geojson`, `.gpkg` via `ST_Read`; `.parquet`/`.geoparquet` via `read_parquet` + WKB decode
- Spatial index removed from DuckLake entirely (button, endpoint, backend fn, post-crawl) — DuckLake can't index; bbox columns + Parquet stats are the fast path
- GeoParquet gotchas: DuckDB's bundled GDAL **cannot** read Parquet via `ST_Read` (use `src.parquet` in duckle); geometry column may be a WKB BLOB (decode with `ST_GeomFromWKB`) **or** a native `GEOMETRY` type (DuckDB-written parquet) — detect via DESCRIBE; CRS comes from the `geo` kv metadata (default `OGC:CRS84`)
- `SELECT * EXCLUDE (OGC_FID)` fails on GPKG (no such column) — use `COLUMNS(c -> c != 'OGC_FID')`
- `db.connect(catalog=...)` accepts a path override; the pipeline's row-count query had silently attached the *default* catalog instead of the one passed to `run_pipeline`
- End-to-end tested: geojson / gpkg / native parquet / WKB geoparquet / zipped geojson all load with identical schemas
